4. **Printer-offline banner** — APPROVED → plan 008.

Original evidence for these findings (kept for the record):

1. **Scheduled prints** — a "morning briefing" widget exists
   (`features/widgets.py:536–577`, `app.py:357–370`) whose whole point is
   mornings, yet every print requires a manual click from the tailnet. The
   pieces are already in place: systemd host (timer + `curl` with the admin
   token and a locally-set `Tailscale-User-Login` header would work with zero
   code), or a small in-process scheduler thread (matches the existing
   worker-thread pattern in `app.py:785–812`). Trade-off: cron-style config
   creep vs. the single most obvious daily-use win for a receipt printer.
   Effort: S (systemd timer) to M (in-app schedules UI). If picked, start as
   a design spike: decide where schedules live (env, DB, or systemd).
2. **Friend doodles / images** — the owner console has a full Image tab
   (upload → dither → print) but friends can only send text. A small canvas
   on `/m/` posted as PNG into the existing queue would reuse
   `features/image.py` wholesale. Abuse surface is the trade-off: images
   can't be content-filtered like text; mitigations already exist (approval
   model, per-user cap 3, and Plan 002's input guards). Effort: M.
3. **Emoji revival via monochrome font** — emoji support shipped and was
   reverted (`b17884a` → `addbce8`, "color-emoji compositing didn't produce
   good prints"). Since then, per-character font fallback landed (`866c9a2`),
   which is exactly the routing a *monochrome* emoji font (e.g. Noto Emoji)
   needs — no compositing involved. Confidence is medium: at 203dpi thermal
   resolution small emoji may still print muddy, and this repo's render
   constants are validated on real hardware only. If picked: spike = render a
   test sheet behind `DRY_RUN`, then one real print of assorted emoji sizes
   before committing to the feature. Effort: M (spike S).
4. **Printer-offline banner on `/m/`** — friends currently learn a print
   failed only after the fact (history row flips to `failed`,
   commit `ab83cca`). The server already knows the offline state
   (`printer.py:_looks_offline`, reset machinery). A cached "printer looks
   offline right now" flag surfaced on the friends page would set
   expectations before they compose. Effort: S. Trade-off: a stale flag is
   worse than none; needs a cheap freshness rule (e.g. cleared on any
   successful print, set on any PrinterError).

## Findings considered and rejected

Recorded so the next audit doesn't re-litigate them:

- **Fetch timeouts in `static/app.js` / `friends.js`**: reported as "a hung
  fetch blocks the UI" — wrong mechanism (fetch is async; per-button
  in-flight states landed in `4cde7bb`). A stalled request leaves one button
  disabled until refresh; not worth code.
- **Offload owner widget prints to the queue**: owner-only, single user;
  `0d1b4e1` already moved rendering outside the USB lock and made HN fetches
  concurrent. Blocking one of four threads for a ~15s briefing is fine.
- **SQLite pooling / multi-worker warning comment**: the warning already
  exists (`auth/db.py:1–8`, README deploy section).
- **CI matrix for `DEV_BYPASS_TAILNET=false`**: the gate is directly tested
  via the `no_bypass` fixture + header injection in `tests/test_security.py`;
  a deploy-time misconfiguration isn't reachable by pytest.
- **Persist login rate-limit buckets**: documented as by-design in-memory
  (`auth/blueprint.py:29`, README).
- **Shorten 30-day friend sessions / add CSRF tokens**: deliberate,
  documented trade-offs (`app.py:42` comment; HttpOnly + Secure + SameSite=Lax
  already set) appropriate to the trust model.
- **gunicorn listed in requirements.txt but never imported**: standard
  practice for a deployed WSGI app; not debt.
- **Unify friend-route error handling under `_safe()`**: shapes are already
  consistent (`{ok, error, kind}`); the one real gap (HTML 500 on DB failure
  in `friend_print`) is fixed by Plan 001 without the refactor.
- **`.env.example` ↔ `config.py` drift-checker script**: over-engineering at
  this size; the audit's "couldn't read .env.example" report was the audit
  sandbox's own restriction, not a repo defect.
- **Ruff/linting in CI**: viable but not planned — the codebase is small,
  consistent, and agent-maintained with a fast test suite; revisit if
  contributor count or file count grows.
- **Worker-loop restructure for "fragile" cleanup ordering** (`_print_worker`):
  speculative; the worker already catches print and DB exceptions per-job.
- **API/extension docs for `features/*`**: module docstrings are strong and
  Plan 004's CLAUDE.md covers the conventions that matter to contributors.
- **LED protocol discovery** (`features/led.py`): intentionally experimental
  scaffolding, blocked on hardware/vendor info, already documented in the
  module docstring — nothing for a code plan to do.
